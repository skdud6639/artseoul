# 아트서울 운영 출시 체크리스트

현재 구현 범위는 B2B 서비스 소개·작품 탐색·관심 작품·실제 상담 저장과 운영자 상담 관리입니다. 아래 항목을 운영자가 확인한 뒤 공개 상담 접수를 활성화합니다.

## 사업 정보와 콘텐츠

- [ ] 대표 브랜드 표기, 실제 운영자명과 개인정보 문의 이메일을 확정한다.
- [ ] 서비스 가능 지역, 설치 가능 조건과 응답·후속 연락 담당자를 정한다.
- [ ] 작품별 소유·위탁·렌탈 권한, 작가 정보와 이미지 사용권을 확인한다.
- [ ] 예시 데이터를 실제 작품으로 교체할 때 치수·매체·액자·이미지·식별값을 검수한다.
- [ ] 실제 가용성·월 렌탈료를 공개하려면 공급·기간·비용 적용 조건을 함께 확인한다.
- [ ] 공간 제안 예시와 실제 설치 사례를 구분하고, 실제 사례에는 고객·사진·로고 공개 동의를 확보한다.
- [ ] 확인되지 않은 작가 학력·기관 전시 이력·전속 관계·고객 실적을 게시하지 않는다.

## 견적과 현장 운영

- [ ] 최소 이용 기간, 작품 수, 월 렌탈료와 계약 총액의 기준을 정한다.
- [ ] 운송·설치·회수·교체·벽면 작업·지역·야간 작업·세금의 포함 여부를 정한다.
- [ ] 교체·연장·중도 종료·구매전환 조건을 견적과 계약에 일치시킨다.
- [ ] 파손·분실·복원·보험 적용과 책임 범위를 실제 공급·보험 계약에 맞춰 확인한다.
- [ ] 실제 재고·보류·계약 일정을 관리할 대장을 마련한다. 관심 저장과 상담 접수로 예약이 확정되지 않게 한다.
- [ ] 벽면·중량·반입·주차·작업 시간·현장 담당자 확인, 출고·설치·회수 상태 기록 절차를 준비한다.
- [ ] 무료 초기 상담과 유료 컨설팅의 범위·산출물·수정 횟수를 확정한다.

견적·계약·재고 일정·설치·정산 도구는 현재 앱에 구현되어 있지 않습니다. 별도 운영 도구나 대장을 마련한 뒤 업무를 진행합니다.

## 접수와 개인정보

- [ ] `.env` 또는 운영 비밀 저장소에 실제 운영자·문의 이메일·보관기간을 설정한다.
- [ ] 운영자만 사용하는 32자 이상의 무작위 `ADMIN_TOKEN`을 발급한다.
- [ ] 토큰을 `VITE_*`, 소스, 커밋, 로그와 공유 URL에 넣지 않는다.
- [ ] 개인정보 안내·동의 목적·보관기간이 실제 운영 및 관련 외부 처리 방식과 일치하는지 검토한다.
- [ ] 정보 열람·수정·삭제 요청의 접수와 본인 확인 담당자를 정한다.
- [ ] 상담 자동 이메일·CRM 알림이 없음을 운영자가 이해하고 상담 관리 화면 확인 절차를 정한다.
- [ ] 개인정보를 불필요하게 메모나 테스트 데이터에 남기지 않는다.
- [ ] 원본과 백업의 보관·삭제·복원 절차를 정한다. 앱의 만료 정리는 백업 파일까지 삭제하지 않는다.

`INQUIRY_ENABLED=true`만으로 접수가 열리지 않습니다. 운영자명·유효한 문의 이메일·1~3650일 보관기간·32자 이상 관리자 토큰을 모두 설정해야 합니다. 활성화 여부는 `/api/inquiry-config`로 확인할 수 있습니다.

## 배포 환경

- [ ] Node.js 24와 잠금 파일 기준 의존성 설치를 확인한다.
- [ ] `npm run build` 후 `npm run serve`로 API와 정적 화면을 함께 제공한다.
- [ ] 운영 시작 디렉터리를 프로젝트 루트로 지정하고 서버의 3000번 포트를 확인한다.
- [ ] HTTPS 프록시와 실제 사이트의 `PUBLIC_ORIGIN`을 설정한다.
- [ ] 프록시를 사용하는 경우 실제 프록시 IP만 `TRUSTED_PROXY_IPS`에 지정한다. CIDR·와일드카드·전체 신뢰를 사용하지 않는다.
- [ ] 프록시가 클라이언트 주소 전달 헤더를 정확하게 설정하는지 확인한다.
- [ ] 데이터베이스 경로를 영구 볼륨에 지정한다. `public/`와 `dist/` 밖에 둔다.
- [ ] 서버 재시작·재배포 후에도 상담 기록이 유지되는지 확인한다.
- [ ] SQLite WAL을 고려한 일관된 백업·복원을 시험하고 원본·백업 접근을 제한한다.
- [ ] 서버 종료·재시작, 디스크 공간, 보관기간 정리 실패를 확인할 운영 절차를 마련한다.

현재 요청 수 제한은 프로세스 메모리에 저장됩니다. 다중 인스턴스와 자동 확장을 도입하려면 저장소와 요청 제한 상태를 공유하는 구조가 필요합니다. 운영자 인증은 단일 토큰 방식이며 역할별 권한·SSO·변경 감사 로그는 포함되지 않습니다.

## 출시 검증

- [ ] `npm run lint`, `npm run format:check`, `npm run typecheck`, `npm test`, `npm run build`를 통과한다.
- [ ] GitHub Actions의 해당 커밋 결과를 확인한다.
- [ ] 모바일·데스크톱에서 6개 메뉴와 작품·작가·공간 제안의 상세 URL을 직접 연다.
- [ ] 작품 검색·필터·결과 없음·초기화·뒤로가기·관심 작품 유지와 삭제를 확인한다.
- [ ] 선택 작품과 서비스·공간 유형이 상담에 전달되는지 확인한다.
- [ ] 운영용과 분리된 데이터베이스에서 접수 활성화·비활성화·잘못된 입력·중복 요청·서버 오류를 확인한다.
- [ ] 실제 저장 성공 후에만 접수 번호가 표시되고 새로고침·재방문에서 허위 완료가 표시되지 않는지 확인한다.
- [ ] 잘못된 토큰으로 운영 API에 접근할 수 없고, 정상 토큰으로 상담 단계·메모를 저장할 수 있는지 확인한다.
- [ ] 키보드로 메뉴·FAQ·작품·상담을 이용하고 포커스·오류 안내·작품 전체 비율을 확인한다.
- [ ] 고객용 안내에 실제 예약·계약·보험·가격 보장으로 오해할 문구가 없는지 검수한다.
- [ ] 운영자와 개인정보 설정 확인 후 `INQUIRY_ENABLED=true`로 접수를 시작한다.

## 후속 개발

실제 문의와 운영 데이터를 바탕으로 견적·계약, 작품 가용 일정, 설치·회수, 결제·정산, 고객 포털과 다지점 권한을 순서대로 확장합니다. 문의가 저장된다는 사실만으로 해당 업무가 자동 처리되는 것은 아닙니다.
